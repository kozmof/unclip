# Architecture

This document is the map: which crate owns what, why the layering is shaped the
way it is, and where the guarantees the code works hardest to establish begin and
end. For what the tool does and how to run it, see the [README](README.md); for
the details of any one type, see its rustdoc.

## Two subsystems, one binary

unclip contains two subsystems that share a SQLite file and a CLI and almost
nothing else. Knowing which one you are in is the first thing to establish when
reading the code, because they have separate vocabularies, separate error types,
and separate validation strategies.

**The possibility space** is the original product and what the README's quick
start covers. It stores addressable *branches*, indexes them by *o2o* and *o2m*
values, constrains them with *frames*, and samples *packets* to feed a model.
Identifiers are plain `String` paths; validation is centralised in
`unclip-core::validate`; errors are `CoreError` and `StoreError`.

**Semantic leveling** is the epistemic engine reached through `unclip level`. It
records *observations*, aligns them to a versioned *domain*, calculates
*measurements* over them, derives *structures*, proposes *candidates*, tests them
against held-out evidence, and records accepted *revisions*. Identifiers are
newtypes generated by `unclip_epistemic::string_id!`; validation lives with each
operation; errors are `PluginError` and `MeasureError`.

They are deliberately not unified. A branch is authored content; an observation is
recorded evidence about the world. The two subsystems touch only in
`unclip-cli`, which dispatches to both, and in the database file, whose tables do
not reference each other across the divide. If you are looking for the seam
between them, it is `crates/unclip-cli/src/app.rs`: everything under
`Command::Level` is subsystem two, everything else is subsystem one.

## Crate layering

Dependencies point strictly downward. No crate depends on one listed below it.

```
            |                              |

                                           |
                                   unclip-observe   101      recorded evidence
                                           |

                                           |
                                   unclip-epistemic 589      operations and provenance
                                           |
                                   unclip-record    171      persistable run records
```

`unclip-epistemic` is the root of the leveling subsystem: 589 lines that every
crate above it depends on and that depends on nothing but `serde` and `semver`.
`unclip-core` plays the same role for the possibility space.

`unclip-record` exists so `unclip-engine` and `unclip-store` can share record
types without either depending on the other. The engine performs no persistence;
routing its record types through the store would make every engine consumer link
SeaORM, SQLx and SQLite to run a calculation. With the split, the engine library
resolves **29** transitive dependencies rather than 192.

### Why the leveling stack is this tall

Each layer exists to be *unable* to do something:

- **`unclip-epistemic`** can construct a `Derived<T, O>`. Nothing else can.
- **`unclip-domain` / `unclip-observe`** hold data with no behaviour, so a
  calculation cannot smuggle logic into the shape of its inputs.
- **`unclip-measure`** calculates and has no notion of provenance, plugins, or
  persistence — it cannot record a result, only return one.
- **`unclip-plugin`** defines the contracts and the registry, and has no
  calculations of its own — it cannot prefer a first-party plugin.
- **`unclip-sensors`** calculates and has no clock, RNG, network, or async
  runtime. CI enforces this by walking the dependency tree
  (`.github/scripts/check-sensor-dependencies.sh`), so a sensor cannot become
  nondeterministic by accident.
- **`unclip-engine`** orchestrates and owns the registry. It cannot persist.
- **`unclip-store`** persists. It cannot calculate.

## The epistemic guarantee, and where it stops

This is the core design idea and the thing most worth understanding before
changing anything in the leveling subsystem.

Every derived value carries the operation that produced it — inferred,
calculated, experimental, or interpreted — in its **type**:

```rust
pub struct Derived<T, O: OperationKind> { /* all fields private */ }
pub type Inferred<T>     = Derived<T, ops::Inference>;
pub type Calculated<T>   = Derived<T, ops::Calculation>;
pub type Experimental<T> = Derived<T, ops::Experiment>;
pub type Interpreted<T>  = Derived<T, ops::Interpretation>;
```

Three mechanisms make that label trustworthy:

1. **`Derived`'s fields are private and `OperationKind` is sealed.** The only
   constructor is `EmitToken::<O>::emit`, and a plugin receives exactly one token
   whose `O` its family fixes. A sensor gets a `CalculationToken`; an interpreter
   gets an `InterpretationToken`. Neither can produce the other's output, and
   `Inferred<T>` cannot be returned where `Calculated<T>` is expected. Both facts
   are pinned by `trybuild` tests with full rendered diagnostics in
   `crates/unclip-plugin/tests/ui/`.
2. **Inputs are read through a context that records them.** `MeasureCtx::read`
   routes through `DependencyCollector`, which inserts into a `BTreeSet`, so
   provenance inputs are automatically sorted, deduplicated, and impossible to
   omit. A value obtained any other way is missing from provenance and breaks
   verification.
3. **Absence is a value, not a sentinel.** `Reading` has four variants —
   `Value`, `NotApplicable { reason }`, `NotMeasured`, and
   `InsufficientEvidence { have, need }`. A sensor whose evidence requirements
   are unmet is never invoked; the engine records *why* instead. Sparse evidence
   is never reported as zero.

**Where it stops.** All of the above is an in-memory guarantee. A value written
to SQLite and read back is a fresh `Tracked<T>` whose operation is whatever the
restoring caller names:

| constructor | meaning |
| --- | --- |
| `Tracked::from_calculated` | the source table admits only calculated values |
| `Tracked::from_inferred` | a replayed inference product |
| `Tracked::from_recorded` | the operation genuinely is not known here |

`require_calculated_evidence` rejects evidence *labeled* as inferred,
experimental, or interpreted. It accepts the unlabeled case, because "no claim
was made" is a real state that import and legacy rows are in. So across the
persistence boundary the compile-time guarantee degrades to a convention:
**call the labeling constructor whose table settles the question.** When you add
a repository read that restores derived values, that is the decision to get
right.

The same split shows up in writes. `MeasurementRepository::insert_calculated_structure`
takes a `Calculated<EmpiricalStructure>` and writes provenance edges with it;
`insert_unverified_structure` takes a plain record and writes none. The names say
which is which.

## What `unclip level verify` proves

It replays the persisted inference products of a recorded run and re-executes the
**calculation** stages against their stored values and provenance. It does not
re-run inference or interpretation, because both call an external model.

So a successful verify establishes: given these recorded observations,
alignments and rankings, these plugin versions and these parameter hashes
reproduce these measurements exactly. It does not establish that the model would
produce the same observations again. The README says so and the code is built
around that limit — `InferenceIo` and `InterpretationIo` are separate traits
precisely so the nondeterministic call is isolated from the logic that interprets
its response, which keeps that logic testable against recorded responses.

There is no HTTP client anywhere in this workspace. The only implementations of
those two traits are file-backed: a model response is authored or captured into a
YAML document, and the interpreter rejects it unless its `model` and
`model_version` match the resolved plugin's.

## Plugin families

A plugin is a descriptor, a context, and an emit token. The descriptor states
identity, version, and a `params_schema`; the context hands over exactly the
inputs that family may see; the token is the only way to construct the return
value. Which token a family receives is its epistemic claim and is not
negotiable.

| family | claim | token |
| --- | --- | --- |
| `Sensor`, `ProductSensor`, `CrossProductSensor` | calculates | `CalculationToken` |
| `Comparator` | calculates | `CalculationToken` |
| `NullModel` | calculates | `CalculationToken` |
| `CandidateGenerator` | calculates | `CalculationToken` |
| `Inferrer` | infers | `InferenceToken` |
| `Experimenter` | tests | `ExperimentToken` |
| `Interpreter` | interprets | `InterpretationToken` |

`Registry` claims a `PluginId` across *all* families, because `EngineProfile`
selects by bare id: a registry that let one id mean two plugins could only ever
expose one of them.

A descriptor's `params_schema` is enforced, not decorative. `classify_sensor`
validates parameters against it before invoking a sensor, so a third-party sensor
is held to its own declared contract on the same terms as a first-party one, and
a violation is recorded as a sparse reading naming the offending key. A
registry-wide test (`crates/unclip-engine/tests/sensor_stage.rs`) asserts every
builtin schema is well formed enough to constrain something.

## Engine surface

`Engine` owns the plugin registry. Its methods are the ones that need it:
stage orchestration (`plan`, `execute`, `infer`, `measure`, `interpret`,
`verify`) and the operations that resolve plugins by id.

Everything stateless is a free function in the crate root — `derive_empirical`,
`generate_candidates`, `compare_measurements`, `record_delta_w_test`, the rest.
These take the `RunPlan` they operate on and construct nothing, so a caller that
wants a pure calculation does not have to build a registry to reach it. They are
free functions rather than `RunPlan` methods only because `RunPlan` belongs to
`unclip-plugin`, and Rust does not allow inherent impls across crates.

## Persistence

One SQLite file. One connection, pinned (`max_connections(1)`), because SQLite
PRAGMAs are connection-scoped and a pool would leave `foreign_keys`,
`busy_timeout` and `journal_mode` set on whichever connection happened to run
them. The CLI is a single short-lived process, so one connection is sufficient
and makes the pragmas unconditional.

Only `unclip init` may create the database. Every other command opens with
`mode=rw`, so the *open itself* — not a racy preflight existence check —
guarantees a typo cannot silently produce a fresh empty archive.

Reads are bounded on purpose. `find` refuses above `MAX_FIND_RESULTS` (10,000)
because it returns fully hydrated branches; `PageCursor` is the single owner of
the pagination invariants, so the short-page rule and the resume key are stated
once rather than re-derived per command. `sample` streams candidates through a
weighted reservoir and is bounded by `--count`; `compose` draws repeatedly from
one pool per slot and therefore has to hold it, which is why it hits the bounded
read instead of paging past it.

Entities are generated by `sea-orm-cli` and then hand-edited — the required
fixups are listed in `crates/unclip-entity/src/lib.rs`, and a test module there
asserts each one, because a regeneration that misses one still compiles while
silently narrowing a 64-bit seed.

## Conventions

- `#![forbid(unsafe_code)]` in every crate.
- Comments explain *why*, not *what*. A comment that describes code that is no
  longer there is a defect.
- CI denies warnings from clippy and rustdoc, runs on three platforms, checks
  `cargo package`, gates supply chain through cargo-deny, and holds line
  coverage at 85%.
- Determinism is a property CI enforces, not a hope: sensors are checked for
  effectful dependencies, and `conformance::assert_sensor` runs a sensor twice
  and compares.
